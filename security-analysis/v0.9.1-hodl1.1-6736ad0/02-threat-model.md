## 3. STRIDE 脅威分析

### 3.1 Spoofing (なりすまし)

#### S-01: Bearer トークンの推測・窃取によるなりすまし

| 項目 | 内容 |
|------|------|
| **脅威** | 攻撃者が有効な Bearer トークンを推測または窃取し、他のユーザーになりすまして Google Workspace API を操作する |
| **リスク** | **HIGH** |
| **攻撃ベクトル** | トークン窃取 (ネットワーク盗聴、ログ漏洩)、ブルートフォース |
| **既存の対策** | (1) 256-bit エントロピーのセキュアトークン生成 (`OsRng` + 32バイト) (2) HTTPS 必須 (localhost以外) (3) `Cache-Control: no-store` ヘッダー (4) 24時間の TTL |
| **残存リスク** | ログへのトークン出力可能性の調査が必要。Cloud Logging にトークンが記録されると漏洩リスクが生じる |

#### S-02: Dynamic Client Registration の悪用 [MCP 仕様準拠]

| 項目 | 内容 |
|------|------|
| **脅威** | 攻撃者が `POST /register` を無認証で呼び出し、不正なクライアントを登録して OAuth フローを開始する |
| **リスク** | **MEDIUM** |
| **攻撃ベクトル** | 認証不要の `/register` エンドポイントへの直接リクエスト |
| **MCP 仕様との関係** | [MCP Authorization Specification](https://modelcontextprotocol.io/specification/2025-03-26/basic/authorization) で Dynamic Client Registration ([RFC 7591](https://datatracker.ietf.org/doc/html/rfc7591)) の実装を **SHOULD** で推奨。RFC 7591 では `/register` は認証なしが標準的な仕様であり、MCP クライアント（Claude Code / Claude Desktop）との互換性のために必要。また `redirect_uri` の検証ルール（localhost or HTTPS のみ）も MCP 仕様の **MUST** 要件に準拠。**アプリケーション層での認証追加は MCP クライアントとの互換性を損なう。** |
| **既存の対策** | (1) redirect_uri のスキーム検証 (HTTPS or localhost — MCP 仕様 MUST 準拠) (2) 登録クライアント数上限 (10,000) (3) PKCE (S256) 必須 |
| **残存リスク** | `/register` が認証不要のため、大量の不正クライアント登録によるリソース枯渇の可能性がある。対策はインフラ層（Cloud Run ingress, レート制限）で実施すべき |

#### S-03: OAuth コールバックの偽装 (CSRF)

| 項目 | 内容 |
|------|------|
| **脅威** | 攻撃者が `/oauth/callback` に偽の state パラメータを送信し、被害者のセッションに攻撃者の Google アカウントを紐付ける |
| **リスク** | **LOW** |
| **攻撃ベクトル** | CSRF 攻撃、state パラメータの推測 |
| **既存の対策** | (1) 256-bit エントロピーの state パラメータ (2) state は pending_auths に保存され一度しか使えない (consume-on-use) (3) 15分の TTL |
| **残存リスク** | 十分に対策されている |

#### S-04: Google OAuth トークンを使った直接 API アクセス

| 項目 | 内容 |
|------|------|
| **脅威** | Secret Manager に保存された Google OAuth トークンが漏洩し、攻撃者が Gateway を迂回して直接 Google Workspace API にアクセスする |
| **リスク** | **CRITICAL** |
| **攻撃ベクトル** | Secret Manager の IAM 設定不備、サービスアカウントキーの漏洩、Cloud Run インスタンスへの侵入 |
| **既存の対策** | (1) Secret Manager に保存 (GCP の暗号化) (2) メタデータサーバー経由の認証 (サービスアカウントキー不要) |
| **残存リスク** | 全ユーザーのトークンが単一シークレットに保存されており、1件の漏洩で全ユーザーの Google Workspace データが危険にさらされる。Secret Manager のバージョン管理により過去のバージョンにもアクセス可能で、トークン漏洩時のローテーション手順が未定義 |

### 3.2 Tampering (改ざん)

#### T-01: 権限設定 YAML の不正変更

| 項目 | 内容 |
|------|------|
| **脅威** | 攻撃者が `config/permissions.yaml` を改ざんし、権限昇格を行う |
| **リスク** | **LOW** |
| **攻撃ベクトル** | Git リポジトリへの不正アクセス、PR レビューのバイパス |
| **既存の対策** | (1) YAML はリポジトリ管理で PR レビュー必須 (2) コンテナイメージに同梱 (ランタイム変更不可) (3) 変更履歴が Git に残る |
| **残存リスク** | リポジトリ管理の運用に依存。ブランチ保護ルールの設定が重要 |

#### T-02: JSON-RPC リクエストの改ざん

| 項目 | 内容 |
|------|------|
| **脅威** | AI エージェントが不正な JSON-RPC リクエストを構築し、意図しない API 操作を実行させる |
| **リスク** | **MEDIUM** |
| **攻撃ベクトル** | 敵対的な AI プロンプトインジェクション、MCP リクエストの直接操作 |
| **既存の対策** | (1) メソッド ID ベースのホワイトリスト権限制御 (2) スコープ + メソッドパターンの二層チェック (3) 未登録ユーザーは全拒否 (deny-by-default) (4) `tools/list` は許可済みメソッドのみ返す |
| **残存リスク** | メソッドのパラメータレベルの制御がない。例: `gmail.users.messages.send` が許可されている場合、送信先や内容の制限はできない。AI エージェントが正当なツール呼び出しの中で悪意あるパラメータを渡す可能性がある |

#### T-03: Secret Manager に保存されたセッションデータの改ざん

| 項目 | 内容 |
|------|------|
| **脅威** | Secret Manager のセッション JSON を改ざんし、他ユーザーのトークンを上書きまたは不正なセッションを挿入する |
| **リスク** | **MEDIUM** |
| **攻撃ベクトル** | Secret Manager への書き込み権限を持つ主体による不正操作 |
| **既存の対策** | (1) Secret Manager の IAM による書き込みアクセス制御 (2) Cloud Run サービスアカウントのみが書き込み可能 |
| **残存リスク** | サービスアカウントに `Secret Manager Admin` ロールが必要と記載されており (README.custom.md)、これは過剰な権限。`Secret Manager Secret Version Manager` で十分だが、シークレットの自動作成のために Admin が必要という設計上のトレードオフがある |

### 3.3 Repudiation (否認)

#### R-01: API 操作の否認

| 項目 | 内容 |
|------|------|
| **脅威** | ユーザーが自身の Google Workspace API 操作を否認する |
| **リスク** | **MEDIUM** |
| **攻撃ベクトル** | 「AI エージェントが勝手に操作した」という否認 |
| **既存の対策** | (1) Cloud Logging への構造化ログ出力 (ユーザー email、タイムスタンプ、メソッド ID、成功/失敗) (2) Cloud Run のアクセスログ |
| **残存リスク** | ログの改ざん防止策 (Cloud Logging のシンク設定、ログの保持ポリシー) の確認が必要。AI エージェントとユーザーの意図的操作の区別が困難 |

#### R-02: 管理者による権限変更の否認

| 項目 | 内容 |
|------|------|
| **脅威** | 管理者が権限設定を変更したことを否認する |
| **リスク** | **LOW** |
| **攻撃ベクトル** | Git 履歴の改ざん |
| **既存の対策** | (1) Git による変更履歴管理 (2) PR レビュープロセス |
| **残存リスク** | 十分に対策されている (Git の署名付きコミットを追加すれば更に強化可能) |

### 3.4 Information Disclosure (情報漏洩)

#### I-01: Secret Manager シークレット漏洩による全ユーザートークン一括露出

| 項目 | 内容 |
|------|------|
| **脅威** | 単一の Secret Manager シークレットに全ユーザーのセッション (Google OAuth refresh_token 含む) が JSON として保存されており、漏洩時の「爆発半径」が最大 |
| **リスク** | **CRITICAL** |
| **攻撃ベクトル** | IAM 設定不備、サービスアカウント侵害、内部脅威 |
| **既存の対策** | (1) Secret Manager による保存時暗号化 (Google 管理鍵) (2) IAM によるアクセス制御 |
| **残存リスク** | **単一障害点**: 1つのシークレットが漏洩すると、約20名全員の Google Workspace データにアクセス可能になる。ユーザーごとのシークレット分離が行われていない。Secret Manager のバージョンは自動削除されないため、古いバージョンにも全セッションデータが残る |

#### I-02: エラーメッセージからの情報漏洩

| 項目 | 内容 |
|------|------|
| **脅威** | エラーレスポンスに内部情報 (スタックトレース、設定情報等) が含まれる |
| **リスク** | **LOW** |
| **攻撃ベクトル** | 意図的な不正リクエストによるエラー誘発 |
| **既存の対策** | (1) Google トークンエラーのレスポンスを500文字に切り詰め (2) `OAuthConfig` の Debug 実装で client_secret を `[REDACTED]` に置換 (3) 汎用的なエラーメッセージ ("Token exchange failed", "Invalid or expired token" 等) |
| **残存リスク** | エラーメッセージに `eprintln!` で email アドレスを出力している箇所がある (http.rs 616行目: `OAuth callback: authenticated user {email}`)。Cloud Logging に記録される可能性 |

#### I-03: OAuth トークンのメモリ内残留

| 項目 | 内容 |
|------|------|
| **脅威** | Google OAuth トークンがメモリ内に平文で保持され、メモリダンプやコアダンプから漏洩する |
| **リスク** | **MEDIUM** |
| **攻撃ベクトル** | Cloud Run インスタンスへの侵入、コアダンプの取得 |
| **既存の対策** | (1) Cloud Run のサンドボックス環境 (2) トークンの TTL 管理と期限切れクリーンアップ |
| **残存リスク** | Rust の `String` 型はメモリ解放後もゼロクリアされない。`secrecy` クレートや `zeroize` の使用なし。Cloud Run のコンテナ環境では実質的リスクは低いが、ベストプラクティスからは逸脱 |

#### I-04: セッション永続化時のバージョン蓄積

| 項目 | 内容 |
|------|------|
| **脅威** | Secret Manager にセッション変更のたびに新バージョンが作成され、過去の全バージョンにアクセス可能 |
| **リスク** | **MEDIUM** |
| **攻撃ベクトル** | Secret Manager の過去バージョンへのアクセス |
| **既存の対策** | なし (Secret Manager のデフォルト動作) |
| **残存リスク** | セッション変更のたびに `addVersion` が呼ばれ、過去のバージョンが無期限に残る。古いバージョンの自動破棄ポリシーが設定されていない場合、漏洩リスクが増大する。また、バージョン数の増加により Secret Manager のコストと管理負荷が増加 |

#### I-05: OAuth スコープの過剰付与

| 項目 | 内容 |
|------|------|
| **脅威** | Google OAuth トークンが全ロールのスコープの和集合を持つため、Gateway の権限制御をバイパスすればトークンが持つ全スコープにアクセス可能 |
| **リスク** | **HIGH** |
| **攻撃ベクトル** | トークン漏洩時、Gateway の権限制御は無効化され、トークンのスコープがそのまま攻撃範囲になる |
| **既存の対策** | (1) README.custom.md に明記: Token-level downscoping は Google Workspace API では不可能 (CAB は Cloud Storage のみ) (2) permissions.yaml でのスコープ絞り込みの推奨 |
| **残存リスク** | **設計上の制約**: Google Workspace API の仕様により、トークンレベルでのスコープ制限が技術的に不可能。Gateway の権限制御層は「アプリケーション層の防御」であり、トークンが直接使用された場合は無力。これは受容すべきリスクだが、トークン保管のセキュリティが極めて重要になる |

### 3.5 Denial of Service (サービス拒否)

#### D-01: Dynamic Client Registration の大量リクエスト

| 項目 | 内容 |
|------|------|
| **脅威** | `/register` エンドポイントに大量のリクエストを送信し、メモリを枯渇させる |
| **リスク** | **MEDIUM** |
| **攻撃ベクトル** | 認証不要のエンドポイントへの DDoS |
| **既存の対策** | (1) `registered_clients` の上限 10,000 件 (2) Cloud Run のスケーリング制限 |
| **残存リスク** | レート制限が実装されていない。10,000件の登録が可能な状態は社内利用 (約20名) に対して過剰。上限に達するまでメモリ消費が増加する |

#### D-02: Pending Auth / Pending Code の枯渇攻撃

| 項目 | 内容 |
|------|------|
| **脅威** | OAuth フローを大量に開始して `pending_auths` や `pending_codes` のメモリを枯渇させる |
| **リスク** | **MEDIUM** |
| **攻撃ベクトル** | `/authorize` への大量リクエスト |
| **既存の対策** | (1) 各マップの上限 (pending_auths: 10,000、pending_codes: 10,000) (2) TTL による自動クリーンアップ (15分/10分) (3) リクエスト処理時のクリーンアップ呼び出し |
| **残存リスク** | `/authorize` は client_id の事前登録が必要だが、`/register` が無認証のためチェーンでの攻撃が可能。上限値が社内利用に対して過剰 |

#### D-03: リクエストサイズによるメモリ枯渇

| 項目 | 内容 |
|------|------|
| **脅威** | 巨大な JSON-RPC ペイロードを送信し、メモリを枯渇させる |
| **リスク** | **MEDIUM** |
| **攻撃ベクトル** | 非常に大きな JSON body を含むリクエスト |
| **既存の対策** | (1) Cloud Run のデフォルトリクエストサイズ制限 |
| **残存リスク** | アプリケーションレベルでのリクエストサイズ制限が見当たらない。axum のデフォルト設定に依存。Cloud Run の制限 (32MB) で保護されるが、明示的な制限の追加が望ましい |

#### D-04: Mutex ロックの競合による応答遅延

| 項目 | 内容 |
|------|------|
| **脅威** | TokenStore への同時アクセスが Mutex で直列化されるため、高負荷時に応答遅延が発生する |
| **リスク** | **LOW** |
| **攻撃ベクトル** | 大量の同時リクエスト |
| **既存の対策** | (1) Cloud Run のインスタンス数制限 (2) 約20名の小規模利用 |
| **残存リスク** | 現在の規模では問題ないが、セッション永続化 (`persist()`) が Secret Manager への HTTP 呼び出しを含むため、Mutex ロック保持時間が長くなる可能性がある。ただし、`persist()` は `await` なので Mutex は解放されている（tokio::sync::Mutex は await 中にロックを保持する設計のため、実際にはロック保持時間が問題になりうる） |

### 3.6 Elevation of Privilege (権限昇格)

#### E-01: 権限制御バイパス — メソッドパラメータの操作

| 項目 | 内容 |
|------|------|
| **脅威** | 権限制御はメソッド ID レベルだが、API パラメータの制御がないため、許可されたメソッドの範囲内で意図しない操作が行われる |
| **リスク** | **HIGH** |
| **攻撃ベクトル** | (1) `gmail.users.messages.send` 許可 → 任意の宛先にメール送信 (2) `drive.files.create` 許可 → 共有ドライブへのファイル作成 (3) 他ユーザーのリソースへのアクセス (userId パラメータの操作) |
| **既存の対策** | (1) メソッド ID ホワイトリスト (2) スコープ制限による間接的な制御 |
| **残存リスク** | **パラメータレベルの制御なし**: Google Workspace API では `userId: "me"` が慣例だが、他のユーザー ID を指定できる API もある。AI エージェントの敵対的入力を前提とすると、メソッド許可だけでは不十分 |

#### E-02: ツール名からメソッド ID への変換の悪用

| 項目 | 内容 |
|------|------|
| **脅威** | `tool_name_to_method_id()` がアンダースコアをドットに置換する単純なロジックであり、意図的に構成されたツール名でメソッド ID の権限チェックをバイパスする |
| **リスク** | **LOW** |
| **攻撃ベクトル** | MCP リクエストで不正なツール名を指定 |
| **既存の対策** | (1) `tools/call` 時にツールがキャッシュ内に存在するか確認 (2) Discovery JSON に定義されたメソッドのみ実行可能 |
| **残存リスク** | ツール名はサーバー側で生成・管理されるため、クライアントが任意のツール名を送信しても実行前にバリデーションが行われる。リスクは低い |

#### E-03: 権限設定ファイルなしでの全アクセス許可

| 項目 | 内容 |
|------|------|
| **脅威** | `--permissions-file` が指定されない場合、認証済み全ユーザーに全メソッドへのフルアクセスが許可される |
| **リスク** | **HIGH** |
| **攻撃ベクトル** | デプロイ時の設定ミス、環境変数の未設定 |
| **既存の対策** | (1) README.custom.md に後方互換性のための仕様として記載 |
| **残存リスク** | **フェイルオープン**: 権限設定ファイルが未指定の場合にデフォルト全許可となる設計は、設定ミスによる意図しないフルアクセス許可のリスクがある。本番環境では必ず permissions-file を指定する運用ルールが必要 |

#### E-04: OAuth スコープの全ロール和集合によるトークン権限の拡大

| 項目 | 内容 |
|------|------|
| **脅威** | OAuth トークンは全ロールの `scopes` の和集合を持つため、reader ロールのユーザーのトークンであっても、トークン自体は admin ロールのスコープを含む |
| **リスク** | **HIGH** |
| **攻撃ベクトル** | トークン漏洩時に、Gateway の権限制御をバイパスして広範なスコープでAPIアクセスが可能 |
| **既存の対策** | (1) Gateway レイヤーでのスコープ + メソッドパターン二層チェック (2) README にて技術的制約として明記 |
| **残存リスク** | **設計上の制約 (受容済み)**: Google Workspace API では Token-level downscoping が不可能なため、全ユーザーのトークンが最大スコープを持つ。これにより、トークン漏洩のインパクトが増大する。トークンの保管セキュリティの強化で軽減すべき |

### CRITICAL 発見事項の詳細

#### CRITICAL-1: 全ユーザーセッションの単一シークレット保存 (S-04 + I-01)

**問題**: 全ユーザー (約20名) の Google OAuth トークン (refresh_token 含む) が単一の Secret Manager シークレットに JSON blob として保存される。この「爆発半径 (blast radius)」は最大であり、1つのセキュリティ侵害で全ユーザーの Google Workspace データが危険にさらされる。

**推奨対策**:
1. **短期**: Secret Manager の IAM ポリシーを最小権限に制限。`Secret Manager Admin` ではなく `Secret Manager Secret Version Manager` を使用 (シークレットの自動作成は初期セットアップスクリプトで対応)
2. **短期**: 古い Secret Manager バージョンの自動破棄ポリシーを設定
3. **中期**: ユーザーごとのシークレット分離を検討 (爆発半径の縮小)
4. **中期**: アプリケーション層での暗号化の追加 (Secret Manager の暗号化に加えて二重暗号化)

### HIGH 発見事項の詳細

#### HIGH-1: パラメータレベルの権限制御なし (E-01)

**問題**: 権限制御がメソッド ID レベルのみで、API パラメータの検証がない。AI エージェントからの敵対的入力を前提とすると、許可されたメソッド内で悪意ある操作が可能。

**推奨対策**:
1. **短期**: 高リスクメソッド (`gmail.users.messages.send` 等) に対するパラメータ検証の追加
2. **中期**: `userId` パラメータを `"me"` に強制する制御の追加
3. **長期**: パラメータレベルのポリシー制御フレームワークの設計

#### HIGH-2: 権限設定なしでのフェイルオープン (E-03)

**問題**: `--permissions-file` 未指定時にデフォルトで全メソッドアクセスが許可される。

**推奨対策**:
1. **短期**: HTTP Gateway モードでは `--permissions-file` を必須引数にする、またはデフォルトで deny-all にする
2. **短期**: 権限設定なしで起動した場合に警告ログを出力する (既に実装されているか確認要)
